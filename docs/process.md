## 1. 阶段 0：选题与约束

### 目标
找一个能写进简历、能在自己电脑上完成、成本 <¥100 的算法项目。

### 约束（很硬）
- 本机是 **Apple M4 / 16GB**，没有 NVIDIA 卡 → 训练必须租卡；
- 预算 ¥100 → 只能租 3090/4090 约 30–60 小时；
- 目标是算法岗 → 面试会深挖 20–30 分钟，必须有可讲的技术细节。

### 选型过程
排除：

| 方向 | 为什么排除 |
|---|---|
| 数学推理 RL（GSM8K） | 太同质化，简历上一抓一大把 |
| 多智能体 | 评测难、成本高 |
| 全参微调 7B | 24G 装不下，预算不够 |
| 从零预训练 | 不可能，也不该声称 |

选中：**多跳检索 Agent（tool use + agentic RL）**。理由：

1. 有环境、有可验证奖励（EM/F1），不需要奖励模型；
2. 单卡能训 1.7B，成本可控；
3. 2026 年招聘热点，且能讲清“为什么需要 agent”。

### 面试怎么讲
> 我先定了三个约束：单卡 24G、预算 ¥100、要经得起深挖。
> 这直接排除了 7B 全参和纯数学 RL，最后选多跳检索，因为它既有环境又有可验证奖励。

## 2. 阶段 1：数据地基

### 目标
把 HotpotQA 变成「可检索语料 + 干净切分」。

### 做法
1. 从 hf-mirror 下 dev 集 distractor parquet（27MB，HF 直连被墙）；
2. 每题 10 个段落，按标题去重 → 66,581 段；
3. 问题 7,405 条，切 eval200 / rl1200 / sft2000，qid 两两不交（seed 42）。

### 撞到的第一个坑：context 是列式 struct
以为 `context` 是 `[{"title","sentences"}]`，实际是：

```python
{"title": array([...10 个标题...]), "sentences": array([[...], [...]])}
```

直接 `ctx[0]` 报 `KeyError: 0`（字典没有 0 键）。

**定位过程**：先打印 `type(ctx)` → dict；再 `repr(ctx)[:200]` → 看到两个并行数组。

**解决**：写 `normalize.py`，兼容三种形态（列式 struct / list-of-struct / 原始二维数组），下游只认 `{"title","sentences"}`。

### 第二个坑：level 列全是 hard
7,405 条里 `level` 全是 `hard`，说明这份导出把该列写坏了。

**处理**：分层只按 `type`（bridge/comparison），报告里明确写“level 不可用”，不拿它做分析。

### 结果
```
corpus 66,581 段（平均 87 词）
questions 7,405
支持事实缺失 0
训练/评测 qid 交集 0
```

### 面试怎么讲
> 数据管线最容易出问题的是 schema 漂移。我做了归一化层，并统计了数据质量——
> 发现 level 列全坏，所以分层只按题型做，避免用错误字段得出错误结论。

## 3. 阶段 2：检索器

### 目标
建 BM25 索引，并证明“检索是有效的”。

### 做法
- 文档 = `title + " . " + text`（标题里常是实体名）；
- 查询去停用词；
- 指标：Recall@k（gold 覆盖率）和 AllHit@k（两段都命中）。

### 三代分词

| 版本 | 分词 | 问题 | R@5 |
|---|---|---|---|
| v0 | `[a-z0-9]+` | `Motörhead` → `mot`+`rhead`，永远搜不到 | 0.613 |
| v1 | 加标题 + 去停用词 | 变音符仍丢 | 0.695（旧分词） |
| v2 | `[^\W_]+`（Unicode） | — | 0.695 |

v1→v2 只影响 200 题里的 7 题，但修复了确定性 bug。

### 关键认知：AllHit@5 只有 0.44
bridge 题的第二跳实体名**不在问题里**（问“某乐队首张未发行录音”，答案段是 Motörhead，但问题里没这个词）。

**这个数字是全项目的论据**：不是检索器不行，是查询必须由模型改写——所以需要多轮 agent。

### 一致性教训
中途发现评测用 `[a-z0-9]+`、训练用 `[^\W_]+`，两套分词 → 同一个模型看到不同检索结果。
统一后重跑，并把这次变更写进 changelog（影响 7/200 题，R@5 0.6925→0.6950）。

### 面试怎么讲
> 我特意没有换向量检索。BM25 的失败模式（词面不匹配）正是多跳任务要解决的问题，
> 而且它零成本、可复现。AllHit@5=0.44 这个上限，就是“为什么需要 agent”的量化证据。

## 4. 阶段 3：协议与工具环境

### 目标
定义模型和工具之间的“接口”。

### 为什么用文本协议
```text
<tool_call>{"name": "search", "arguments": {"query": "Motörhead band"}}</tool_call>
<answer>Song Il-gon</answer>
```

- 评测、训练、数据生成可以共用同一个 parser；
- 不依赖特定推理框架的工具抽象；
- 模型在预训练里见过这种形式。

### 代价
和 TRL 的结构化 `tool_calls` 不兼容——这是后来 GRPO 第一次失败的直接原因（见第 8 节）。

### SearchEnv 设计
```python
reset(question, answer, supporting_titles)   # 每轮重置
search(query) -> str                         # top-3，每条 ≤60 词
calculator(expression) -> str
```
- 索引是**类级单例**，避免每次 rollout 重建（重建一次 30 秒）；
- 观测截断，控制上下文；
- 工具报错以文本返回，让模型自己重试。

### 面试怎么讲
> 我做了一个关键取舍：协议自己定义、parser 自己写，换来训练/评测/蒸馏三处一致。
> 代价是要和 TRL 的工具抽象打架，后来确实在这里踩了坑。

## 5. 阶段 4：基线

### 目标
量出“没训练过的模型有多差”，并拆解错误来源。

### 过程
1. 0.6B × 20 题，跑了 5 次（调试指标、修 parser、加 lenient 口径）；
2. 0.6B × 200 题：EM 0.040、tag_rate 0.20、avg_calls 0.95；
3. 1.7B × 200 题：EM 0.140、tag_rate 0.745、avg_calls 1.62。

### 关键发现：em_contains 0.27 vs EM 0.04
27% 的输出里**其实有正确答案**，只是没包进 `<answer>`。

**结论**：瓶颈是协议，不是知识。这直接决定了 SFT 数据的重点。

### 2×2 分解
| | 答对 | 答错 |
|---|---|---|
| 检索到 gold | 27 | 157 |
| 未检索到 | 1 | 15 |

**结论**：检索不是瓶颈（tool_hit 0.92），作答才是。

### 面试怎么讲
> 我没有只看 EM。加了一个 em_contains 指标后发现，27% 的答案其实是对的，
> 只是没按格式交卷。这个观察决定了后面 SFT 的重点是协议和两跳，而不是知识。

## 6. 阶段 5：SFT 数据

### 目标
造 2,000 条“会搜、会二次搜、会按协议答”的轨迹。

### 为什么用强模型蒸馏
自己采样（0.6B/1.7B）通过率太低，且不会示范“第二跳”；用 DeepSeek-V4.1-Flash 生成，成本 ¥5.5。

### 三类数据

| 类型 | 生成 | 保留 | 教什么 |
|---|---|---|---|
| A 格式 | 1,200 | 287 | comparison 题，协议 |
| B 两跳 | 2,600 | 1,367 | bridge 题 |
| C 弃答 | 400 | 187 | 假实体 → unknown |

### 关键技巧：oracle 首跳
对一半 B 类样本，人工注入“正确第一跳查询 + 真实检索结果”，教师只需学第二跳。
通过率从 ~40% 提到 65%。

### 撞到的坑：DeepSeek 422
```
422 ... messages[3]: missing field `tool_call_id`
```
DeepSeek 要求 `role: tool` 必须配结构化 `tool_calls`。

**解决**：发给教师的观测改成 `role=user` + `[TOOL OUTPUT]` 前缀；
**落盘的 SFT 数据仍是 `role=tool`**（和训练/评测一致）。

### 过滤规则的三次演进
1. 严格 EM → 保留率 40%，误杀大量别名答案（`Alan Turing` vs `Alan Mathison Turing`）；
2. 加 F1≥0.8 和“包含 gold 且不啰嗦” → 保留率 60%；
3. 弃答样本封顶 10% → 防止模型过度拒答。

### 数据问题
`wrong_answer` 丢了 1,149 条（29%），属于正常损耗；
A 类通过率只有 24%（comparison 题对教师也难），导致 A 只占 16%。

### 面试怎么讲
> 数据不是“造了 4,200 条”，而是造了 4,200、留下 1,937。
> 我用了回放校验（重放工具调用，观测必须逐字一致）来挡掉环境漂移的样本，
> 这条规则挡掉了 10–20% 的脏数据。

## 7. 阶段 6：SFT 训练

### 配置
LoRA r=32、α=64、7 个投影层；2 epoch；有效 batch 8；lr 1e-4；max_len 3072；bf16 + 梯度检查点。

### 关键技术点：assistant-only loss
只在模型生成的 token 上算 loss，工具返回的段落被 mask 掉。

**为什么**：观测是外部文本，训练它等于教模型“复述检索结果”。

**风险**：如果模板不支持（缺 `{% generation %}`），掩码会为空，训练等于白做。
**解决**：脚本里加 preflight，打印“多少 token 带 loss”，为 0 直接退出。

### 撞到的坑：warmup_ratio 不认
```
TypeError: SFTConfig.__init__() got an unexpected keyword argument 'warmup_ratio'
```
transformers v5 把该参数移除了。

**解决**：按函数签名过滤未知参数，并打印被丢弃的字段——这样换环境不会再崩。

### 结果
| 指标 | 基线 | SFT |
|---|---|---|
| EM | 0.140 | **0.405** |
| tag_rate | 0.745 | 0.960 |
| avg_calls | 1.62 | 2.21 |
| no_answer | 0.255 | 0.040 |

train_loss 0.289、eval_loss 0.2575（低于 train，无过拟合）、entropy 0.21。

### 新问题
4% 的题跑满 5 轮（max_turns_hit 8）——学会了“多搜”，没学会“何时停”。

### 面试怎么讲
> SFT 涨了 26.5 点，但我更关注它暴露的新问题：max_turns 4%。
> 这正好接上 RL 的动机——用工具预算奖励教它“什么时候停”。

## 8. 阶段 7：GRPO（三轮失败 + 一轮修复）

### 动机
SFT 只模仿；GRPO 用组内相对优势优化最终奖励，理论上能学出示范外策略。

### 第一次失败：奖励恒为 −0.025

现象：
```
rewards/answer_reward/mean = 0
completions/mean_length = 23
```

打印原始 completion 后看到：
```
[assistant tool_calls=[search(...)] content='']
[tool name=search] [1] Scout Tufankjian: ...
[assistant content='<tool_call>{']     ← 第二轮崩
```

**定位**：读 TRL 源码发现**工具返回内容也算进 `max_completion_length`**（默认 256）。
一次检索 3 段 × 60 词 ≈ 240 token，加上调用直接超预算 → TRL 丢弃工具结果 → 模型没看到资料。

**修复**：`max_completion_length=1024`。reward 终于有值。

### 第二次失败：50 步内 reward 从 0.41 掉到 0.37，calls 2.21→2.03

**定位**：lr 5e-6 太大 + λ=0.1 让“少搜”比“答对”更划算。

**修复**：lr 1e-6、λ 0.02、temperature 0.8。仍然下降。

### 第三次失败：reward 0.44→0.29，clipped_ratio 0.375

**定位**：37.5% 的 completion 被截断，坏样本污染梯度；除 std 有难度偏置。

**修复**：
- `max_completion=2048`（3 次检索也装得下）
- `mask_truncated_completions=True`
- `loss_type="dr_grpo"`（去掉 std 归一化的难度偏置）
- `entropy_coef=0.001`
- `max_turns=3`

### 第四次：终于收敛（持平）

40 步，400 题 × group 4：

| 指标 | SFT | GRPO |
|---|---|---|
| EM | 0.405 | 0.405 |
| F1 | 0.531 | 0.536 |
| tag_rate | 0.960 | 0.965 |
| avg_calls | 2.21 | 2.19 |

训练侧 reward 0.416→0.462，clipped 0.375→0.00。

**归因**：单卡 batch 16、轨迹级奖励无 step-level 信用分配、1.7B 容量接近上限。

### 面试怎么讲（这是最能加分的一段）
> GRPO 我失败了三次。第一次是 reward 恒为 0，读 TRL 源码发现工具结果占了 completion 预算，
> 被静默丢弃；第二次是学习率太大加预算惩罚过重，模型学会“少搜”而不是“答对”；
> 第三次是 37.5% 的样本被截断污染梯度。修完之后训练稳定了，但评测只是持平——
> 我把它归因于 batch 规模和奖励粒度，而不是算法本身。

## 9. 阶段 8：RFT

### 做法
用 SFT 模型对 500 题各采 3 条 → 过滤出 592 条正确轨迹 → 与全量 SFT 数据 1:3 混合（2,433 条）→ 再训 1 epoch。

### 结果
EM 0.395、F1 0.525、tag_rate 0.980、calls 2.19。

### 为什么没涨
- 592 条只来自约 200 道题（同题多分支），有效多样性低；
- 拒绝采样是“模仿自己的好样本”，信息上限就是采样分布；
- eval_loss 0.125 偏低，模型对 RFT 数据拟合紧但没有泛化增益。

### 面试怎么讲
> RFT 是离线方法，收益取决于采样多样性而不是数量。我 500 题 × 3 条只有 200 个独立问题，
> 所以涨不动。这也反过来说明在线方法（GRPO）在有足够 batch 时才有意义。

## 10. 阶段 9：评测方法学

### 指标
EM、F1、em_contains、tag_rate、avg_calls、tool_hit_rate、no_answer_rate、max_turns_rate。

### 2×2 分解
检索 × 正确，把“检索问题”和“推理问题”分开。

### 统计可靠性
200 题 95% CI ≈ ±7 点；所以：

- 1–2 点的差异不宣称显著；
- 报告里给点估计 + CI；
- 评测必须 greedy，保证可复现。

### 泄漏检查
```python
assert not (train_qids & eval_qids)
```
实测为 0。

### 面试怎么讲
> 我知道 200 题的 CI 是 ±7 点，所以我从不说“提升了 2 个点”。
> 这也是为什么 RL 阶段我写的是“持平”，而不是“微涨”。

## 12. 最终结论

1. **SFT 贡献了几乎全部收益**（+26.5 点）；
2. **RFT/GRPO 在 200 题上无统计显著差异**；
3. **瓶颈迁移**：从“协议遵循”（tag 0.20→0.96）转到“检索到了答不对”（hit_wrong 157→111）；
4. **负结果的归因**：batch 规模、评测方差、轨迹级奖励的信用分配。

> 我选了多跳检索，因为它有环境、有可验证奖励。
> 数据侧我先建了 6.6 万段语料和 BM25 索引，发现单次检索的两跳命中率只有 0.44，
> 这证明问题不是检索器，而是查询要改写——所以需要 agent。
> 然后我用 DeepSeek 在真实环境上蒸馏了 1,937 条轨迹，做了 LoRA SFT，
> EM 从 0.14 到 0.405，格式合规率从 0.75 到 0.96。

> 37.5% 的样本被截断。修完之后训练稳定，但评测持平，我归因于单卡 batch 和奖励粒度。

### 追问树（面试官可能怎么挖）

**问：为什么不直接用 function calling？**
答：文本协议能让训练、评测、蒸馏共用一套 parser；代价是和 TRL 的结构化工具抽象不兼容。

**问：AllHit@5=0.44 说明什么？**
答：说明单次检索在词面上不可能覆盖两跳，必须靠模型改写查询。这是 agent 存在的理由。

**问：SFT 数据 1,937 条够吗？**
答：够学行为，不够学知识。我做了回放校验和难度分层，通过率 46%。

**问：为什么 GRPO 没涨？**
答：三个原因：batch 16 太小、200 题 CI ±7 点、轨迹级奖励没有 step-level 信用分配。

**问：如果重做一次？**
答：先做 pass@k 和更大 batch 的 GRPO；或者把 0.6B 的 GRPO 跑通再上 1.7B。

## 14. 如果重做一次

1. **先做评测再训练**：我花了不少时间在数据生成上，但评测基线才是判断一切的锚点；
2. **GRPO 先上 0.6B**：1.7B 的失败成本太高；
3. **奖励设计从简**：先只留 EM，再加 format，最后加 budget——一次加一项；
4. **数据多样性优先于数量**：500 题 × 5 条比 1,000 题 × 2 条更有用；
5. **保留全部原始 completion**：定位问题时，打印原文比看指标快 10 倍。
